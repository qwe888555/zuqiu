# 人员档案与账号流程：后端改造说明

> 目标：把人员建档权限从管理员下沉到学校，管理员只处理规则、重复档案和异常；球队只能从本校已审核运动员中选人；邀请不再产生无档案账号。
>
> 本文只描述后端需要做的调整，前端会先完成不依赖这些接口的改造部分。

## 1. 现有问题

1. `POST /people` 仅 `ADMIN` 可调用，所有学生档案都必须由管理员逐个创建，规模上不可持续。
2. `POST /accounts/registration-invitations` 的 `personId` 可选，允许创建未绑定人员档案的运动员/教练账号。
3. `POST /auth/registrations` 只创建账号，不创建人员档案；注册时填写的姓名、身份证、手机号没有落到人员主档。
4. `POST /teams/{id}/members/search` 只按姓名搜索，且不限制学校，球队可以搜到外校运动员。
5. `POST /teams/{id}/members` 不校验人员是否属于球队所属学校。
6. 人员档案没有批量导入接口，管理员只能逐条录入。

## 2. 权限与数据范围

### 2.1 建档权限

建议调整为：

| 角色 | 权限 |
| --- | --- |
| `ADMIN` | 全局建档、批量导入、合并重复档案 |
| `UNIVERSITY`（学校） | 仅本校范围内建档、批量导入、提交审核 |
| `CITY` / `PROVINCE_REVIEWER` | 只读、抽查、异常处理，不直接建档 |
| `TEAM` | 不建档，只从本校人员池选人 |

服务端必须校验：

- 学校账号提交的 `schoolOrgId` 必须等于本账号所属学校；
- 不允许通过修改请求体把人员挂到其他学校；
- 跨校人员转入走单独流程，不做静默覆盖。

### 2.2 人员可见范围

- 学校：仅本校人员；
- 市州：本行政区内学校人员；
- 省级/管理员：全省；
- 球队：仅本校已审核运动员（用于组队和报名）。

## 3. 人员批量导入接口（建议新增）

### 3.1 下载模板

```http
GET /people/imports/templates/person.xlsx
```

权限：`ADMIN`、`UNIVERSITY`。

模板列：

| 列 | 必填 | 说明 |
| --- | --- | --- |
| 姓名 | 是 | 与证件一致 |
| 身份证号 | 是 | 18 位，服务端校验校验位与全局唯一性 |
| 手机号 | 是 | 11 位手机号 |
| 人员类型 | 是 | 运动员 / 教练员 |
| 学校 | 是 | 组织编码或学校全称；重名时必须填编码 |
| 学历 | 否 | 自由文本 |
| 性别 | 否 | 男 / 女 / 未说明；留空由身份证推导 |
| 出生日期 | 否 | `YYYY-MM-DD`；留空由身份证推导 |

### 3.2 批量导入

```http
POST /people/imports
Content-Type: multipart/form-data
```

字段：

- `file`: `.xlsx`
- `mode`: `VALIDATE_ONLY` | `APPLY_VALID_ROWS`，与报名名单导入保持一致
- `schoolOrgId`: 可选；学校账号不传时使用本账号所属学校，管理员可指定

返回：

```json
{
  "batchId": "pib_xxx",
  "mode": "APPLY_VALID_ROWS",
  "total": 24,
  "successCount": 23,
  "failureCount": 1,
  "errors": [
    {
      "rowNumber": 9,
      "field": "idNumber",
      "code": "DUPLICATE_RESOURCE",
      "message": "该证件号已存在档案"
    }
  ]
}
```

规则：

- 每行创建一份 `DRAFT` 人员档案，按 `kinds` 创建运动员/教练员扩展档案；
- 身份证号、手机号加密存储，不返回明文；
- 文件内重复、库内重复、学校不存在、学校越权、格式错误均逐行返回；
- `APPLY_VALID_ROWS` 只写入有效行；
- 整个文件最多 500 行，超过直接拒绝；
- 学校账号只能导入本校人员。

### 3.3 错误清单

```http
GET /people/imports/{batch_id}/errors.csv
```

复用报名导入的错误清单格式，返回 UTF-8 BOM CSV。

## 4. 邀请与注册

### 4.1 邀请必须绑定人员档案

`POST /accounts/registration-invitations`：

- `personId` 改为必填（`ATHLETE` / `COACH`）；
- 校验人员存在、未删除、具备对应身份；
- 校验人员未绑定其他账号；
- 校验人员所属学校与邀请组织一致；
- 同一人员不能同时存在两张未使用邀请。

### 4.2 注册接口

`POST /auth/registrations`：

- 若邀请 `person_id` 为空，直接返回 `400 INVALID_ARGUMENT`；
- 注册时填写的 `realName` 必须与人员档案姓名一致；
- `idNumber` 必须与人员档案身份证号匹配；
- 匹配通过后账号绑定该 `personId`；
- 不允许仅凭姓名/身份证“认领”未绑定档案。

### 4.3 未绑定账号治理

建议提供一个管理员查询：

```http
GET /accounts?unbound=true
```

返回 `roles` 包含 `ATHLETE`/`COACH` 且 `personId` 为空的账号，供管理员补绑定或停用。

## 5. 球队候选搜索与成员校验

### 5.1 候选搜索

`POST /teams/{id}/members/search`

调整为：

- 仅返回与本球队所属学校一致的人员；
- 仅返回 `audit_status = APPROVED` 的运动员；
- 排除本队 `CURRENT` 成员；
- 支持按姓名或身份证号后四位搜索；
- 后四位命中多人时全部返回并标记，不能静默取第一条；
- 仍限制最多 20 条，超出时返回 `hasMore`，前端提示缩小关键词。

建议请求体：

```json
{ "keyword": "张伟" }
```

返回人员摘要增加：

- `schoolOrgId`
- `schoolName`
- `maskedIdNumber`
- `auditStatus`

### 5.2 添加成员

`POST /teams/{id}/members`

新增校验：

- 人员必须存在且具备运动员身份；
- 人员必须已审核通过；
- 人员所属学校必须等于球队所属学校；
- 跨校人员返回 `409 STATE_CONFLICT`，错误信息提示走转入流程；
- 球衣号唯一规则保持不变。

## 6. 审核流程建议

当前约束：

- `personCreate` 仅 `ADMIN`；
- `personReview` 仅 `UNIVERSITY`；
- 禁止审核自己创建或最近提交的档案。

下沉建档后需要明确：

1. 学校录入 → 档案 `DRAFT`；
2. 学校提交 → `PENDING`；
3. 审核人：
   - 方案 A：学校内另一管理员账号审核（推荐，满足防自审）；
   - 方案 B：市州/省级抽查；
   - 方案 C：学校单人账号时，允许提交后由市州审核。
4. 审核通过 → `APPROVED`，进入球队可选人员池。

不能出现“学校建档、学校自己立即通过且无任何留痕”的闭环；至少保留审计日志和抽查机制。

## 7. 无身份证学生（业务决策项）

当前 `PersonCreate` 服务层强制要求 18 位身份证号，且 `id_card_hash` 全局唯一。

如果业务确认存在完全没有身份证号的学生，需要先决策：

- 是否允许学籍号作为唯一身份；
- 是否增加 `identity_type` / `identity_no`；
- 与身份证号并存时的查重、转学、跨校合并规则；
- 报名与资格审核如何展示。

在规则确定前，前端不得用姓名、临时编号或手机号冒充身份证号写入人员档案。

## 8. 数据治理

上线前建议执行：

1. 统计现有 `ATHLETE` / `COACH` 且 `person_id` 为空的账号，通知所属机构补绑定或停用；
2. 统计球队现役成员与球队所属学校不一致的记录，交由学校确认；
3. 统计同一身份证号重复档案，管理员合并；
4. 对已存在但未审核的人员档案，明确是否允许继续组队/报名。

## 9. 验收标准

- 学校账号只能在本校范围建档和导入；
- 未绑定人员的运动员/教练账号无法创建；
- 邀请注册后账号必然绑定人员档案；
- 球队搜索不到外校人员；
- 添加外校人员返回 409；
- 人员姓名或身份证后四位均可搜索；
- 管理员不再需要逐条录入学生档案；
- 所有人员变更、审核、邀请、绑定操作均有审计日志。

## 10. 前端已落地的临时措施（不替代后端）

在上述接口上线前，前端先做了以下收紧，均为现有接口范围内的过渡方案：

1. **管理员批量建档**：人员管理新增 Excel 批量导入，浏览器解析后按行调用现有 `POST /people`，有界并发、逐行报错、自动跳过本页会话内已成功的人员。它只减轻管理员录入量，不能替代“学校端建档”。
2. **邀请必须绑定档案**：单个邀请表单要求选择人员档案，并校验档案身份与受邀身份一致；生成按钮在未绑定或身份不一致时禁用。后端仍接受空 `personId`，因此学校/市州若绕过前端仍可能产生无档案账号，需后端强制。
3. **账号补绑提示**：参赛账号列表标出当前页未绑定档案的运动员/教练账号，并提供“补绑”入口；编辑保存时前端已要求运动员/教练必须绑定档案。
4. **球队选人提示**：候选人列表标注外校与未审核状态，加入前二次确认。由于真实后端 `team_out` 不返回 `orgId`，跨校判断退化为学校名称比对，只能提醒，不能阻断，也不能替代后端校验。
5. **无身份证照片**：报名名单中的球员可在“编辑”里逐人上传照片，不依赖身份证号命名，已覆盖小学生无身份证场景。
